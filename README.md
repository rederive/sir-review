# SIR review

A GitHub Action that reviews [SIR](https://github.com/rederive/sir-spec) contract changes in pull requests, in plain
English, and **fails like a test** when a change can't be trusted.

SIR contracts are precise because machines check them, but people approve them, and a reviewer skimming a diff misses
what matters. This action reads both sides of the PR and says it in words:

- **One PR comment**, updated on every push. It covers every changed contract: each change as a phrase-level diff, marked
  🧪 *tested* (held by the hidden tests) or 📝 *note* (prose nobody grades), plus the whole contract in plain English.
- **Notes on the lines** of the tested parts that changed.
- **A failing check with annotations** for every Stop, like a failed assertion pointing at its line.
- **A per-contract report** in the job summary:

  | | unit | change | tests | bindings | citations |
  |---|---|---|---|---|---|
  | ❌ | `strip` | Rule 2, CODE (grammar) | ✗ 1 answer rewritten | ✓ | ✗ contradicted |
  | ✅ | `strip_ansi` | new contract | ✓ 16 from node@24.16.0 | js ✓ | ✓ |

Nothing is generated by a model. Every sentence is the contract's own text or a fixed phrase for its directive, so the
review can't claim anything the files don't. It never writes to a `.sir` file.

**The code that runs is itself verified.** Every pure part of the review lives in [`vendor/review-core`](vendor/review-core):
the plain-English reading, the change list and its Stop rules, the test-file diff, the word diff, hunk lines, line numbers,
the binding check, escaping, annotations and the report. Each part went through rederive's own loop:
1. A sighted decomposer wrote its SIR contract.
2. Tests were stamped from a pinned snapshot, plus independent anchors where they exist: git for line numbers and GitHub's
   own `@actions/core` for escaping.
3. Three blind JavaScript emitters and three blind TypeScript emitters rebuilt it from the contract alone.
4. The JavaScript and TypeScript versions were cross-checked on 2,000 more inputs.

The loop found about 40 bugs in the first hand-written version. Those included ways to rewrite a hidden test answer without
a Stop, injected diff headers, and Markdown injection into the job summary. The Action ships the verified emissions; only
the orchestration (git and the GitHub API) is hand-written.

CI re-checks this on every build:
- `rdv check vendor/review-core` (every unit against its contract);
- a differential that runs this build and rederive's original side by side on 200 seeded pull requests and requires
  byte-identical output;
- a check that `dist/` matches a fresh build.

## What counts as a Stop

| Stop | why |
|---|---|
| A tested part (a rule, a pin, the inputs) changed, but no test did | Nothing in the PR proves the new behavior. The hidden tests still expect the old one. |
| An existing test's answer was rewritten under `FIDELITY package`, and the `ANCHOR` didn't move | The answers were captured from the original package. Running it again gives the old answer, so the new one came from the author. `rdv check` passes, because the test now agrees with the change it's supposed to check. |
| A changed part still cites the original package as the reason for its old behavior | The edit contradicts its own citation. |
| A new contract whose test file doesn't match the fingerprint it declares, or whose language files aren't bound to it | The contract and its tests disagree. |

When a change is intentional (the package really changed), move the `ANCHOR` (`colors@1.4.0` → `colors@1.5.0`) and
re-capture the tests from the new version. When you want different behavior, add a new unit with its own source of truth.
Like a failing test, a Stop blocks merging only if you make the check required in branch protection.

## Usage

```yaml
# .github/workflows/sir-review.yml
name: SIR review
on:
  pull_request:
    paths: ['**/*.sir', '**/oracles/*.json']
permissions:
  contents: read
  pull-requests: write
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: rederive/sir-review@v1
```

Pin by commit SHA (`rederive/sir-review@<sha>`) for the strongest guarantee about what runs in your CI. That's good
practice for any third-party action.

| input | default | |
|---|---|---|
| `fail-on` | `stop` | `stop` fails the check on a Stop. `never` only reports. |
| `comment` | `true` | the PR comment |
| `line-notes` | `true` | the notes on changed lines |
| `github-token` | `${{ github.token }}` | needs `pull-requests: write` for the comment and notes |

## Other CI systems

The engine is `rdv review` in the [`rederive`](https://www.npmjs.com/package/rederive) npm package, and this action
bundles it:

```sh
npx -p rederive rdv review --base origin/main                 # the review, as Markdown; exit 1 on a Stop
npx -p rederive rdv review --base origin/main --format summary  # the per-contract table
```

`--format github` prints GitHub annotations, and `--format json` prints the findings. `--fail-on never` always exits 0.

## Development

`dist/index.cjs` is committed, because actions run from the repo's files. To rebuild it, run `npm run build`. It bundles
`src/` with rederive's review orchestration, taking every pure part from `src/verified.mjs` (the vendored review-core), and
it fails if the orchestration imports anything that isn't redirected.

| command | what it checks |
|---|---|
| `npm run check-core` | the vendored units against their contracts (needs `typescript` and `@types/node`, which are dev dependencies) |
| `npm test` | the 200-PR differential |
| `npm run check-dist` | the committed build against a fresh one |
